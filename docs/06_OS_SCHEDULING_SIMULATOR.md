# ExamOS — OS Scheduling Simulator Specification

**Version:** 0.2 · **Status:** Draft — OS Module Design

## 1. Purpose and boundary

The OS Scheduling Simulator is a faculty/admin-only educational tool that demonstrates scheduling algorithms over **abstract jobs**. It is logically independent from real exam attempts and must not read or modify examination tables. It does not reproduce kernel scheduling and does not schedule browser sessions.

## 2. Input model

Each job contains:

- `id`: unique non-empty label.
- `arrival_time`: integer >= 0.
- `burst_time`: integer >= 1.
- `priority`: integer when Priority Scheduling is selected.
- `input_order`: implicit stable index assigned from submitted order.

Round Robin additionally needs `quantum >= 1`. Limit job count with configuration to protect the UI and algorithm from excessive input. Reject empty job lists, duplicate IDs, booleans/non-numeric values where integers are required, negative arrivals, non-positive bursts, invalid priorities, and invalid quantum. Return field-level validation errors.

## 3. Scheduling definitions

### FCFS

Non-preemptive. Choose ready job with earliest arrival; for equal arrival times, lower `input_order` first. A running job continues until its burst completes. If the ready queue is empty, the CPU is idle until the next job arrives.

### Round Robin

Preemptive time-sharing with a positive integer quantum. Ready jobs are queued FIFO. At a time-slice boundary, first enqueue all jobs arriving at that exact time in ascending `input_order`, then enqueue the unfinished running job at the tail. If the running job completes exactly at the boundary, it is not re-enqueued. When no job is ready, record an idle interval until the next arrival. Context-switch overhead is zero.

### Priority Scheduling

Non-preemptive. Select the ready job with lowest numeric priority value; ties are resolved by arrival time, then original `input_order`. A running job is not preempted by a newly arrived higher-priority job. If no job is ready, record CPU idle time until the next arrival.

## 4. Output model and formulas

For each job report:

- `first_start_time`: first CPU start.
- `completion_time`: time its remaining burst reaches zero.
- `turnaround_time = completion_time - arrival_time`.
- `waiting_time = turnaround_time - burst_time` (valid under zero context-switch overhead).
- `response_time = first_start_time - arrival_time`.

For the run:

- `total_burst_time = sum(job.burst_time)`.
- `measurement_window = latest_completion_time - earliest_arrival_time`.
- `cpu_utilization_percent = 100 * total_burst_time / measurement_window` when the window is positive.
- Averages are arithmetic means across all jobs.
- Timeline is a chronological list of `{job_id, start, end}` and explicit `{job_id: null, start, end, kind: "IDLE"}` intervals.

Explain the measurement window in the UI. Given all jobs have positive burst and at least one job, the window should be positive; defensively handle a non-positive denominator.

## 5. Pure implementation contract

Implement a pure function conceptually like:

`simulate(algorithm, jobs, quantum=None) -> ScheduleResult`

The function must not access FastAPI request objects, database sessions or UI state. Validate input before simulation or return structured validation errors. For deterministic output, preserve original `input_order` in tie-breaks. The Gantt builder must use the exact schedule segments generated by the algorithm; do not reconstruct timing separately from metrics.

Recommended internal types: `JobInput`, `ExecutionSegment`, `JobMetrics`, `ScheduleResult`. Keep them simple dataclasses or Pydantic models depending on the existing module style.

## 6. Expected invariants

- Every valid job executes exactly its burst time.
- A job does not execute before its arrival.
- No two execution segments overlap.
- A job's completion follows its first start and all its execution segments.
- `turnaround = completion - arrival`.
- `waiting = turnaround - burst`.
- `response = first_start - arrival` and is non-negative.
- Total busy time equals the sum of burst times.
- Idle periods are explicit and do not count as busy time.
- Same input yields same output.

## 7. Hand-verifiable reference cases

### Case A — FCFS with idle interval

Jobs in input order:

| ID | Arrival | Burst | Priority |
|---|---:|---:|---:|
| A | 0 | 3 | 2 |
| B | 5 | 2 | 1 |

Expected timeline: `A [0,3)`, `IDLE [3,5)`, `B [5,7)`. Metrics:

| Job | First start | Completion | Turnaround | Waiting | Response |
|---|---:|---:|---:|---:|---:|
| A | 0 | 3 | 3 | 0 | 0 |
| B | 5 | 7 | 2 | 0 | 0 |

Window is 7, total burst is 5, utilization is `5/7 × 100 ≈ 71.43%`.

### Case B — Round Robin, quantum 2

Jobs:

| ID | Arrival | Burst |
|---|---:|---:|
| A | 0 | 5 |
| B | 1 | 3 |

Using the specified boundary rule, timeline: `A [0,2)`, `B [2,4)`, `A [4,6)`, `B [6,7)`, `A [7,8)`. Expected metrics:

| Job | First start | Completion | Turnaround | Waiting | Response |
|---|---:|---:|---:|---:|---:|
| A | 0 | 8 | 8 | 3 | 0 |
| B | 2 | 7 | 6 | 3 | 1 |

### Case C — Non-preemptive Priority

Jobs:

| ID | Arrival | Burst | Priority |
|---|---:|---:|---:|
| A | 0 | 4 | 3 |
| B | 1 | 2 | 1 |
| C | 1 | 1 | 2 |

A starts at 0 and completes at 4. Then B wins priority over C and runs `[4,6)`, then C runs `[6,7)`. Metrics:

| Job | First start | Completion | Turnaround | Waiting | Response |
|---|---:|---:|---:|---:|---:|
| A | 0 | 4 | 4 | 0 | 0 |
| B | 4 | 6 | 5 | 3 | 3 |
| C | 6 | 7 | 6 | 5 | 5 |

These cases are part of the test suite and should be supplemented by a same-time-arrival test and a Round Robin simultaneous-arrival/quantum-boundary test.

## 8. UI requirements

- Selector for algorithm.
- Editable job rows and sample-workload buttons.
- Quantum visible only when Round Robin is selected.
- Priority visible/required for Priority Scheduling.
- Run button and input validation.
- Gantt-style axis with execution and idle segments.
- Per-job metrics table, averages and utilization.
- Optional side-by-side run comparison, only after the basic simulator is correct.
- Visible disclosure: “Educational simulation of abstract jobs; not real kernel scheduling.”

## 9. Test plan

Unit tests include all reference cases, one job, all jobs arriving at zero, idle start, idle gaps, same-arrival ties, same-priority ties, RR with one job, RR arrival exactly at a quantum boundary, invalid inputs, and high-but-configured job count. Add invariant/property-style tests where practical.
